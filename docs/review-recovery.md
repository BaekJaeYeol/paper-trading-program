# 검증 후 선택 기록 복구

## 범위

미국 Alpaca 모의계좌에서 원래 주문 조건이 복원되고 종료된 경우에만 수동 검토 기록을 해소한다.
대상 코드는 `price_changed`, `fields_changed`다. 정정·교체, ID, 수량, 체결 감소 사건은 지원하지 않는다.
기업행위나 새 주문 체인을 승인하거나, 저장된 주문·체결 원문을 덮어쓰지 않는다.

## 화면 흐름

1. 다른 실행 프로세스를 종료하고 `비상 중단`을 적용한다.
2. 증권사에서 원래 주문 조건과 체결 내역을 직접 확인한다.
3. `계좌·주문 대조` 후 `차단 상세`에서 지원되는 활성 기록을 선택한다.
4. `선택 기록 복구 점검`에서 확인 내용을 읽고 진행한다. 취소하면 복구 작업을 시작하지 않는다.
5. 신규 GET 조회·동기화에 모두 통과해야 선택한 기록 하나만 해소한다.
6. 차단 상세에는 해소 이력이 남고 주문 변경 기록에는 `수동 검토 해소 · 재개 아님`이 표시된다.

다른 활성 기록은 유지된다. STOP은 유지하며 자동매매는 재개하지 않는다.
재개는 기존 `모의매매 시작`의 별도 대조와 STOP 해제 확인을 다시 거친다.
실계좌 주문은 활성화하지 않는다.

## 필수 검증

- `cycle.lock`이 전 과정을 배타 보호하고, STOP 파일이 처음과 해소 직전 모두 존재한다.
- 계좌 지문 일치, 계좌 권한 정상, 전체 복구 대조 60초 미만.
- 모든 저장된 부모·자식 주문이 확인된 종료 상태이고, 이전 형식/미확인 주문이 없다.
- 조회된 미체결 주문이 없고, 관리 대상 종목의 기대/실제 잔고가 모두 일치하며 0이다.
- 원래 요청과 주문 조건이 일치하고, 기존 체결·ID 검증도 통과한다.
- 선택한 사건의 버전이 확인 시점과 같다. 다른 조회가 사건을 갱신했으면 거부한다.

잔고 0 검증은 관리 대상 종목에 한정하며 다른 수동 보유를 승인하거나 매도하지 않는다.
브로커 여러 GET은 원자적 스냅샷이 아니다. 다른 프로그램이나 사용자의 동시 주문을 기술적으로 막지는 못한다.
종료·무보유 조건은 해당 위험을 줄이기 위한 보수적 범위이며 실계좌 안전성 보장이 아니다.

## 저장과 장애

사건 해소, 고정된 확인 근거 코드, 사건 버전, KST 시각, 주문 이력과 진입 게이트를 같은 DB 트랜잭션으로 반영한다.
복구 중 조회 실패·계좌 변경·STOP 변경·취소·저장 실패가 발생하면 해소하지 않는다.
한 번 해소한 토큰은 재사용할 수 없다. 같은 문제가 다시 관측되면 사건이 다시 활성화된다.
API 키·사용자 자유 입력 확인 메모는 저장하지 않는다. 집계 진단 내보내기는 기존 허용 필드만 사용한다.

## 검증 범위

단위 테스트: 성공/해소 이력, STOP 사전 조건, 미체결/자식 미종료/보유 차단, 미해결 변경과 오래된 토큰,
미지원 사건, 다른 차단 유지, 계좌 변경·조회 실패·중간 STOP 변경·취소, 트랜잭션 롤백, 지연 및 GUI 확인 취소.
Windows GUI CI: 실제 선택·확인 취소·동의·신규 조회·해소 표시와 STOP/다른 차단/주문 수 유지.
브로커는 오프라인 fixture다. 실제 증권사 및 사용자 PC 실행은 미검증이다.

기존 차단 상세의 버튼 줄에 복구 점검 버튼과 확인 모달을 추가하는 설계다.
