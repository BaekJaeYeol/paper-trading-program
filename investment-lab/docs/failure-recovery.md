# PC·서버 장애와 복구

이 문서는 같은 저장소의 두 실행 경로를 구분합니다. `investment-lab`은 GitHub에서 운영하는47개 전략의 가상 체결 연구이고, Windows GUI는 Alpaca/KIS 모의계좌 연결 프로그램입니다. 연구 상태 복구 명령은 GUI 주문 상태를 복구하거나 증권사에 주문하지 않습니다. 별도 토스 프로젝트의 복구도 대신하지 않습니다.

## 증상별 대응

| 문제 | 프로그램의 대응 / 복구 순서 |
|---|---|
| PC 종료·정전·절전 | 꺼지거나 잠든 PC에서는 실행할 수 없습니다. 전원·인터넷을 복구하고 실행 프로그램이 하나인지 확인합니다. 연구는 저장한 기준 봉부터 재개하며 같은 봉의 중복 모의 체결을 막습니다. 증권사 GUI는 실제 모의계좌의 주문·보유를 먼저 대조한 뒤 연결·재개합니다. |
| 같은 폴더를 두 번 실행 | 연구 tick과 세션에 OS 파일 잠금을 적용해 두 번째 실행을 거부합니다. 정상/강제 종료 시 OS가 잠금을 해제하므로 잠금 파일을 임의 삭제하지 않습니다. 서로 다른 PC·복사 폴더의 중복 실행까지 막는 분산 잠금은 아닙니다. |
| 저장 폴더 교체 도중 종료 | 원본 폴더가 없고 `.backup`만 남으면 JSON·계좌 기준 봉·SQLite를 검증한 뒤 교체 전 백업을 복구합니다. `.pending`은 확정된 계좌로 간주하지 않습니다. |
| 현재 폴더와 백업이 모두 남음 | 현재 폴더가 유효하면 그대로 유지하고 이전 백업을 `recovery-archives`에 별도 보존합니다. 현재가 손상됐거나 미완료 저장만 있으면 멈추며 덮어쓰지 않습니다. |
| 디스크 공간 부족·쓰기 권한 오류 | 교체용 복사본 두 개와64MiB 여유를 확보할 수 있는지 먼저 확인합니다. 부족하면 종목 갱신을 중단합니다. 계좌 파일을 지우지 말고 다른 다운로드·로그 등을 백업 후 정리하고 권한을 확인합니다. 검사 뒤 다른 프로그램이 디스크를 채우는 경우도 있으므로 저장 실패 자체도 처리합니다. |
| 상태·운영 이력 JSON 저장 중 오류 | 같은 파일시스템의 임시 파일에 기록하고 flush/fsync 후 교체합니다. 쓰기·교체 실패 시 기존 JSON을 유지합니다. 이미 손상된 파일은 자동으로 빈 계좌·빈 이력으로 바꾸지 않습니다. |
| JSON/SQLite 손상·기준 봉 불일치 | 해당 종목을 중단하고 원본과 백업을 보존합니다. 진단 결과를 보고 마지막 정상 커밋·외부 백업을 대조합니다. 임의로 수량·잔고를 수정하거나 새 계좌로 덮어쓰지 않습니다. |
| 인터넷·데이터 공급자 장애 | 기존 제한된 재시도와 기준 봉·지연 검사를 사용합니다. 실패 종목은 이전 계좌를 보존하고 오류를 기록합니다. 누락 봉이나 중요한 가격 수정은 건너뛰지 않습니다. 네트워크 복구 후 재개합니다. |
| GitHub 업로드 실패 | 로컬 커밋과 원격 저장을 구분합니다. 새 파일 변경이 없어도 남아 있는 미업로드 커밋을 다시 push합니다. 충돌은 자동 강제 덮어쓰지 않습니다. 원격 저장을 마치기 전에는 새 실행을 계속 진행하지 않습니다. |
| GitHub 실행기 강제 종료 | 원격에 올라간 마지막 커밋까지만 보존이 확실합니다. `always` 저장 단계가 실행되지 않을 수 있습니다. 자체 PC/서버의 남은 로컬 상태는 삭제하지 말고 원격과 비교합니다. 원격에 없는 가상 처리분을 재계산할 수 있으며 증권사 주문 재전송과는 다릅니다. |
| 예약 시작 지연·세션 미기동 | 보고서 시각·Actions 실행 기록·누락 회차 경고를 확인합니다. 세션이 시작되지 않으면 새 경고도 생성되지 않습니다. GitHub cron의 정시 기동은 보장할 수 없으므로 개장부터 운영이 필수면 상시 서버/외부 기동기가 필요합니다. |
| PC 시간·서버 시간 오류 | Windows의 자동 날짜/시간·시간대와 시간 동기화를 확인합니다. 서버도 시간 동기화를 복구합니다. 잘못된 시계에서 거래를 계속하지 않습니다. 모든 시간 오차를 자동 검출하는 기능은 추가하지 않았습니다. |
| API 키 만료·재발급·프로그램 재시작 | GUI에는 올바른 모의투자 키를 다시 입력합니다. 키·접근토큰은 파일로 백업하지 않습니다. 반복 인증 오류를 무한 재시도하지 않습니다. |
| 주문 요청 뒤 응답을 못 받음 (GUI) | 주문이 접수됐을 수 있습니다. 증권사 모의계좌에서 client_order_id·미체결·체결·잔고를 먼저 확인합니다. 상태 DB 삭제·같은 주문 재전송은 금지합니다. 연구용 가상 체결 복구 명령으로 해결하지 않습니다. |

## 연구 상태 읽기 전용 진단

실행을 멈춘 뒤 연구 상태 폴더를 지정합니다. Windows PowerShell 예시이며 Linux에서는 `py -3.12` 대신 `python`을 사용합니다.

```powershell
py -3.12 investment-lab/state_recovery.py --state saved-state/intraday-state
```

JSON 계좌, 기준 봉, 필수 SQLite 파일과 `PRAGMA quick_check`, DB·요약의 잔고 일치, 상태/이력 JSON 형식을 검사합니다. 기본 진단은 계좌를 수정하지 않으며 API 키·인터넷이 필요 없습니다. 오류가 있으면 종료코드1입니다. SQLite quick_check는 모든 경제적 오류·과거 손익의 정확성을 입증하는 검사가 아닙니다.

교체 중단 상태가 명확할 때만 다음 명령으로 복구합니다. 일반 실행도 같은 복구를 먼저 수행합니다.

```powershell
py -3.12 investment-lab/state_recovery.py --state saved-state/intraday-state --recover
```

동시 실행을 잠금으로 차단하고 검증된 백업만 사용합니다. 이전 백업/미완료 복사본은 `recovery-archives`에 보존하므로 디스크 사용량이 늘 수 있습니다. 확인한 보관본은 별도 저장장치로 백업한 뒤 관리하세요. 임의의 손상 파일을 추측해서 고치는 기능은 없습니다.

## 정상 저장본에서 수동 복구할 때

1. 관련 프로그램을 모두 멈추고 현재 상태 폴더 전체를 다른 위치에 복사합니다. GUI의 주문 상태 DB나 `STOP` 파일을 연구 폴더와 혼동하지 않습니다.
2. Actions 로그와 `paper-hourly-state`의 커밋을 비교해 마지막 **정상 상태**를 찾습니다. 최신 날짜라고 무조건 정상인 것은 아닙니다.
3. 정상 커밋을 별도 작업 폴더에 내려받아 위 진단을 실행합니다. 상태 요약 한 파일만 다른 날짜의 계좌와 섞지 않습니다.
4. 정상임을 확인한 연구 상태를 사용해 단독으로 재개합니다. 기존 오류본과 Git 이력은 보존합니다. 원격 이력을 강제 push하거나 `reset --hard`로 장애 증거를 삭제하지 않습니다.
5. 재개 후 기준 봉·계좌 수·신규 처리 수·오류·복구 메시지·원격 저장 성공을 확인합니다. GUI는 이 절차와 별도로 증권사 주문·잔고를 대조합니다.

## Windows 운영과 한계

사용자 PC의 절전 설정·재부팅·작업 스케줄러를 이 변경에서 직접 조작하지 않습니다. 설정 → 시스템 → 전원에서 전원 연결 중 절전 시간을 검토하고, 노트북은 덮개 동작과 배터리도 확인하세요. 재부팅 후 GUI는 다시 실행하고 메모리 전용 키를 입력해야 합니다. 키를 배치파일이나 작업 스케줄러 인수에 저장해 무인 재연결하지 않습니다.

연구의 OS 잠금은 Windows와 Linux 경로를 구현하고 CI에서 프로세스 강제 종료 후 잠금 해제를 검사합니다. 사용자의 Windows11 하드웨어에서 실제 정전·절전·네트워크 단절을 일으킨 검증은 아닙니다. atomic replace·fsync·교체 전 검증도 디스크 고장·파일시스템 손상·모든 전원 장애를 막지는 못하므로 독립 백업이 필요합니다. 복구 코드는 실계좌 주문을 실행하지 않습니다.

참고: [Python os.replace/fsync](https://docs.python.org/3/library/os.html), [SQLite PRAGMA quick_check](https://www.sqlite.org/pragma.html#pragma_quick_check), [Git push](https://git-scm.com/docs/git-push).
