# 장중 실행 간격 보완

## 확인한 원인
2026-10-15 실행 기록에서 예약 이벤트 생성 자체가 몇 시간 간격으로 발생했다. 생성 이후 실행은 약 2분이었다. cron 문자열이 잘못된 문제가 아니라 GitHub의 지연·누락 가능성 때문에 매회 별도 예약에 의존하는 구조가 불안정했다.

## 변경
- UTC 평일 11~21시 매시 7분은 세션 시작·재시작 기회다. 매시간 반드시 새 러너가 추가되는 것은 아니며 실행 중인 세션은 취소하지 않는다.
- 예약으로 시작한 러너는 최대 5시간30분 동안 UTC 매시 7·22·37·52분에 수집한다. 매회 수집 소요 시간을 15분에 더하지 않는다. 세션 시작 직후 한 번 확인하고 이후 고정 시각에 맞춘다.
- NYSE 거래일 달력·서머타임을 사용하고 개장 3시간30분 전부터 폐장 30분 후까지만 세션을 유지한다. 휴일은 종료한다.
- 매 회차마다 계좌·상태·HTML을 GitHub에 저장한다. 대기 중 매분 저장소를 동기화하며 비상 중단 파일을 발견하면 즉시 보호 상태를 저장하고 세션을 종료한다. 네트워크·GitHub 장애 시 즉시 중단 감지는 보장되지 않는다.
- 비상 중단 실행은 별도 동시 실행 그룹으로 세션 뒤에 대기하지 않도록 한다. 시작 요청 자체의 지연은 가능하다.
- 일봉 작업은 별도 그룹을 유지하고 두 작업 모두 저장 전 원격 변경을 rebase한다. 푸시 경합은 최대 3회 재시도하며 충돌 시 중단한다. 강제 푸시하지 않는다.
- 일정 실행에서는 브라우저 설치·화면 검사를 반복하지 않는다. 코드 변경·수동 확인 시에는 단일 수집과 브라우저 검사를 실행한다.

## 한계·운영 비용
계속 실행하는 러너 사용 시간이 기존 단발 실행보다 늘어난다. 현재 공개 저장소의 표준 ubuntu-latest 러너만 사용하며 유료 외부 서버를 새로 생성하지 않는다. 공개 범위·요금제 변경 시 비용을 다시 확인해야 한다. GitHub의 첫 시작과 세션 교체 지연·러너 장애는 남으므로 정확한 15분 실행의 SLA를 보장하지 않는다. 그런 보장이 필요하면 독립 상시 서버·외부 스케줄러가 필요하다.

## 검증
주입 시계로 900초 반복·수집 시간에 따른 누적 지연 없음·휴장·마감·단발 실행·대기 중 비상 중단·저장 실패 중단을 검사한다. 실제 증권사 주문은 없다. 실제 장중 연속 간격은 배포 후 운영 이력에서 관찰해야 한다.
